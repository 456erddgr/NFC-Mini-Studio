# 原理说明

这份文档讲清楚三件事：

1. 原厂私有协议是怎么被逆出来的
2. 三条传输通道各自怎么实现、为什么能共用同一套业务逻辑
3. 密钥破解（mfkey32 / HardNested）到底在算什么

#### 1.1.1 关于「小程序更新」的核查（2026-10-17）

有人提到小程序更新过，为此做过一次完整的重新抓取，结论是**服务端并没有发布新版本**。证据链：

| 检查项 | 结果 |
| --- | --- |
| 微信小程序运行时目录 | `%APPDATA%\Tencent\xwechat\radium\users\<用户哈希>\applet\packages\wxc3dd33d9d4ae0fd6\75\__APP__.wxapkg` |
| 缓存包大小 / 时间 | 1 827 808 字节 / 2026-10-02 21:11:42 |
| 强制重下 | 把 `packages\wxc3dd33d9d4ae0fd6` 改名让微信认为本地无缓存，重开小程序后微信于 2026-10-17 11:04:16 重新下载了同一个包 |
| 新包与旧包对比 | 解密后 SHA-256 **完全相同** = `eec82fd56b400a8e1236f44759a331d1fd4d9def3fd908b11db0938304f394cc` |
| `wx.getUpdateManager` 日志 | 2026-10-02 / 10-05 / 10-08 / 10-09 / 10-17 五次全部 `{"hasUpdate": false}` |

也就是说：小程序的「变化」如果存在，只能是**云端热更新**——配置、卡库、问答这些通过 `wx.request` 从
`https://nfctools.nfcreader.net/nice-json/mini-program/v1` 拉取，不走 `wxapkg` 包更新。
协议层（命令字、帧格式、应答布局）自 2026-10 起没有变动，因此本项目移植的协议实现是最新的。

> 如果你确实发现小程序里出现了本项目没有的功能，请开 issue 并附上截图与操作步骤，
> 大概率那是纯云端内容（比如问答条目、卡库配色），不需要改协议层。

小程序是 Taro + React 编译产物，业务逻辑被压在一个大文件里，但**命令名是明文的**：

```js
Object(c.i)(n, t, { opName: "get_device_info" })
Object(c.i)(n, t, { opName: "search_card" })
```

把这些 `opName` 全部 grep 出来，再和固件里的命令分发表对齐，就能复原命令字表。

### 1.2 帧格式

```
短帧（DATA ≤ 255 字节）
┌────┬─────┬───────┬──────────────┬─────┬────┐
│ FF │ LEN │ MSGID │     DATA     │ SUM │ FE │
└────┴─────┴───────┴──────────────┴─────┴────┘
  1B   1B     1B      LEN 字节        1B   1B

长帧（DATA > 255 字节）
┌────┬───────┬───────┬───────┬──────────┬─────┬────┐
│ FD │ LEN_H │ LEN_L │ MSGID │   DATA   │ SUM │ FE │
└────┴───────┴───────┴───────┴──────────┴─────┴────┘
  1B    1B      1B      1B     LEN 字节     1B   1B
```

- `LEN` = DATAB 长度（不含头尾、不含 SUM）
- `SUM = sum(DATA) & 0xFF`
- `MSGID` 由主机分配，1..253 循环，**应答必须原样带回**
- 尾字节固定 `FE`

实现见 `app/protocol.py` 的 `build_frame()` / `FrameParser`。

### 1.4 状态码位置（关键坑）

不同命令的行为差异很大：有的把状态放在 `DATA[1]`，有的放在 `DATA[2]`。`protocol.py` 用 `STATUS_INDEX` 表统一：

```python
STATUS_INDEX = {
    0x05: 1, 0x11: 1,
    0x06: 2, 0x07: 2, 0x08: 2, 0x09: 2, 0x0A: 2, 0x0B: 2,
    0x21: 1, 0x25: 1, 0x30: 1, 0x22: 1,
    0x20: 2, 0x32: 1, 0x34: 1, 0x35: 1, 0x36: 1, 0x37: 1,
}
```

取不到时缺省为 1。`_status_code(data)` 就按这个表取值。

### 1.6 寻卡应答的两种布局

`0x11` 是最容易写错的命令。

**普通卡（≤4 字节 UID）**：

```
[0]  = 0x11
[1]  = 状态（0 = 成功）
[2]  = 卡类型（1=IC, 2=UID, 3=ID, 4=7字节UID）
[3..7) = UID 4 字节（反序！）
[7]  = SAK
[8]  = is_uid_card
```

**注意：设备返回的 4 字节 UID 是反序的**，必须 `uid_reverse()` 翻回来才是人看到的顺序。

**7 字节 UID 卡（type == 4）**：

```
[0]  = 0x11
[1]  = 状态
[2]  = 4
[3..10) = UID 7 字节（正序，不翻）
[10] = SAK
[11] = is_uid_card
```

## 二、三条传输通道

### 2.1 统一抽象

`app/transport.py` 定义了所有通道的契约：

```python
class Transport:
    kind: str          # "ble" / "pcsc" / "net"
    label: str         # 中文显示名
    on_data: Callable[[bytes, str], None]   # 收到字节时回调（必须回完整帧）
    connected: bool

    def open(self, **kw) -> None: ...
    def close(self) -> None: ...
    def send(self, frame: bytes) -> None: ...
```

上层 `NfcDevice` 只做一件事：

```python
def request(self, data: bytes, timeout=5.0, retries=0):
    msgid = self._next_id()
    frame = build_frame(data, msgid)
    event = threading.Event()
    self._waiters[msgid] = (event, None)
    self.transport.send(frame)
    event.wait(timeout)
    return self._waiters.pop(msgid)[1]
```

收到的字节一律交给 `FrameParser.feed()`，按 msgid 唤醒对应的 waiter。

**所以只要新通道的 `on_data` 能回出一个合法的完整帧，业务层就完全不用改。**

### 2.2 蓝牙 BLE 通道

对应 `app/transport.py` 的 `BleTransport`。基于 `bleak`。

关键参数：

| 项 | 值 |
| --- | --- |
| 服务 UUID | `0000FFE0-0000-1000-8000-00805F9B34FB` |
| 写特征 | `0000FFE2-0000-1000-8000-00805F9B34FB` |
| 通知特征 | `0000FFE1-0000-1000-8000-00805F9B34FB` |
| 分包大小 | 普通 180 字节 / 小包 20 字节 |

发送时按 180 字节切片。BLE 单次写有 MTU 上限，包太大读卡器会丢弃，所以发完要小睡一下。

接收走 `start_notify`，每收到一段就调 `on_data`。

这个通道能力最全，因为所有硬件级操作（采集随机数、低频读卡、封卡）都是固件完成的。

### 2.3 通用 PC/SC 通道

对应 `app/transport_pcsc.py`。核心难点：**PC/SC 只认 APDU，不认私有帧**。

思路是做一层「协议翻译网关」：

```
业务层  request(data) ──► build_frame ──► PcscTransport.send(frame)
                                                 │
                                                 ▼
                                          _unframe(frame)
                                          → (msgid, data)
                                                 │
                                                 ▼
                                          _dispatch(data)
                                          按 data[0] 分派
                                                 │
                                                 ▼
                              winscard.dll: SCardTransmit(APDU)
                                                 │
                                                 ▼
                                    按原私有格式拼 reply 帧
                                                 │
                                                 ▼
                              self.on_data(reply)  ← 完完整整的一个帧
```

上层完全感知不到中间发生了什么，因为它收到的就是一个合法的应答帧。

#### winscard.dll 绑定

纯 ctypes，不依赖 `pyscard`（那个要编译）。必需的服务函数：

```c
LONG SCardEstablishContext(DWORD scope, void*, void*, SCARDCONTEXT*);
LONG SCardReleaseContext(SCARDCONTEXT);
LONG SCardListReadersW(SCARDCONTEXT, LPCWSTR, LPWSTR, LPDWORD);
LONG SCardConnectW(SCARDCONTEXT, LPCWSTR, DWORD share, DWORD proto,
                   SCARDHANDLE*, LPDWORD activeProto);
LONG SCardDisconnect(SCARDHANDLE, DWORD disposition);
LONG SCardTransmit(SCARDHANDLE, LPCSCARD_IO_REQUEST, const BYTE*, DWORD,
                   LPCSCARD_IO_REQUEST, BYTE*, LPDWORD);
LONG SCardGetStatusChangeW(SCARDCONTEXT, DWORD timeout,
                           SCARD_READERSTATE*, DWORD count);   // ← 注意是 Change 不是 Changes
LONG SCardFreeMemory(...) / SCardIsValidContext(...)
```

**踩过的坑**：函数名是 `SCardGetStatusChangeW`。拼错成 `SCardGetStatusChangesW` 会 `AttributeError`。

另一个坑：查「卡片在不在」不能用 `SCardStatusW`（它要求已有 hCard 句柄）。正确做法是用 `SCARD_READERSTATE` + `SCardGetStatusChangeW`：

```python
st = SCARD_READERSTATE()
st.szReader = reader_name
st.dwCurrentState = SCARD_STATE_UNAWARE   # 0
code = dll.SCardGetStatusChangeW(ctx, 0, byref(st), 1)
# 首次调用一定返回 0x8010000A = SCARD_E_TIMEOUT
# 但 st.dwEventState 已经被填好了，所以要把 TIMEOUT 当成功处理
present = bool(st.dwEventState & SCARD_STATE_PRESENT)  # 0x20
```

#### APDU 映射

读卡器按 PC/SC 规范提供这组「存储卡」伪 APDU：

| 功能 | APDU | 说明 |
| --- | --- | --- |
| 装密钥 | `FF 82 00 <slot> 06 <key×6>` | `slot` = 0 表示 KEY A，1 表示 KEY B |
| 认证 | `FF 86 00 00 05 <slot> <0> <block> <keyType> <0>` | 成功返回 `90 00` |
| 读块 | `FF B0 00 <block> 10` | 返回 16 字节 + `90 00` |
| 写块 | `FF D6 00 <block> 10 <data×16>` | 返回 `90 00` |
| 读 UID | `FF CA 00 00 00` | 返回 UID + `90 00` |

状态字解释（`sw_text`）：

| SW | 含义 |
| --- | --- |
| `90 00` | 成功 |
| `63 00` | 认证失败（密钥错） |
| `69 82` | 安全状态不满足（没先认证） |
| `6A 82` | 块不存在 / 越界 |
| `6A 81` | 功能不支持 |
| `63 00` | 校验失败 |
| `6F 00` | 命令执行错误 |

#### 命令翻译示例

**密钥校验（0x06）**：

```python
# 请求 data = [0x06, block, key0..key5]
slot = 0                       # 0x06 是 KEY A
load  = bytes([0xFF,0x82,0x00,slot,0x06]) + key
auth  = bytes([0xFF,0x86,0x00,0x00,0x05, slot,0x00, block, keyType,0x00])
ok = transmit(load)==OK and transmit(auth)==OK
reply = bytes([0x06, block, 0 if ok else 8])
```

**读块（0x07）**：

```python
# 需要先确保该扇区已认证
auth_sector(block)
sw, body = transmit(bytes([0xFF,0xB0,0x00,block,0x10]))
if sw: reply = bytes([0x07,0x00]) + body + pad16
else:  reply = bytes([0x07, status])
```

**写 UID（0x27）**：

```python
# uid 6 字节 → 取前 4 作为新 UID，第 5 字节是 BCC
new_uid = uid[:4]
bcc = new_uid[0]^new_uid[1]^new_uid[2]^new_uid[3]
block0 = new_uid + bytes([bcc]) + b"\x08\x04\x00" + b"\x00"*8
auth_sector0(); transmit(bytes([0xFF,0xD6,0x00,0x00,0x10]) + block0)
```

#### 认证状态缓存

同一个扇区认证一次就够了，重复认证既慢又可能触发卡片保护。所以维护：

```python
self._authed: Dict[Tuple[int,int], bool] = {}   # (sector, keyType) -> True
self._loaded_key: Optional[Tuple[bytes,int]] = None
```

卡片拿走再放回时，用 `_reconnect_if_needed()` 清空缓存重新建立连接。

#### 不支持的命令

遇到 `0x20 / 0x22 / 0x30 / 0x32 / 0x25 / 0x26 / 0x17 / 0x23 / 0x40 / 0x41` 直接合成失败应答，抛的中文提示是：

> 通用读卡器不支持「XXX」：该功能依赖原厂固件的硬件能力。请改用原厂 NFC Mini 读卡器（蓝牙）执行；其余寻卡 / 读块 / 写块 / 写 UID / 整卡导出功能在通用读卡器上均可用。

### 2.4 手机读卡器通道

分两半：电脑端 `app/transport_net.py`（客户端）+ Android 端（服务端）。

#### 发现机制

手机端每 1.5 秒往 `255.255.255.255:8766` 广播 UDP 文本包：

```
NFCMINI/1 <设备名> <ip> <port>
例：NFCMINI/1 Pixel-8 192.168.1.5 8765
```

电脑端 `NetTransport.discover()` 在 8766 端口监听 3 秒，解析出候选列表。

**踩过的坑**：一开始把 `len(parts) >= 5` 当条件才取端口，但格式只有 4 段，端口永远读不到。正确写法是 `len(parts) >= 4` 时取 `parts[3]`。

#### 连接握手

TCP 连上后，手机先发一行：

```
NFCMINI/1 <设备名> <ip> <port>\n
```

电脑端 `_read_loop` 检测到缓冲以 `NFCMINI` 开头，就把第一个 `\n` 之前的内容剥掉，剩下的才是帧数据。

#### 帧循环

手机端 `ReaderServer`：

```java
List<Protocol.Frame> frames = parser.feed(buffer);
for (Protocol.Frame f : frames) {
    byte[] reply = engine.dispatch(f.data);
    byte[] out = Protocol.buildFrame(reply, f.msgid);   // msgid 原样带回
    output.write(out);
}
```

电脑端就是普通的 socket 读写，`on_data` 直接喂原始字节。

#### 手机端怎么调 NFC

`NfcEngine` 用 Android 的 `NfcAdapter.enableReaderMode()`，`onTagDiscovered` 拿到 `Tag`，然后 `NfcA` + `MifareClassic` 操作。

- `0x11` 寻卡：从 `tag.getId()` 取 UID，按 4 字节**反序**回（对齐私有协议）
- `0x06/0x09` 认证：`MifareClassic.authenticateSectorWithKeyA/B()`
- `0x07` 读块：`MifareClassic.readBlock()`
- `0x08/0x16/0x18` 写块：`MifareClassic.writeBlock()`
- `0x27` 写 UID：`NfcA.transceive()` 直接发 `A0` 写块 0

扇区号换算（Mifare Classic 1K / 4K 不同）：

```java
static int sectorOfBlock(int block) {
    return block < 128 ? block / 4 : 32 + (block - 128) / 16;
}
```

#### 写块的布局歧义

私有协议 `0x08` 有三种布局（数据在前/密钥在前/只有数据），手机端无法从请求里确定是哪一种。`handleWriteBlock08` 的做法是：

1. 剩余长度 ≥ 22 时，先用**后 6 字节**当密钥试认证；成功 → `data_then_key`
2. 否则用**前 6 字节**当密钥试认证；成功 → `key_then_data`
3. 两种都试过不行，再兜底「只有数据，用默认密钥」

KEY A / KEY B 都试一遍，认证结果进缓存避免重复。

## 三、密钥破解原理

### 3.1 Mifare Classic 的认证过程

```
读卡器                             卡片
   │  ① 认证请求 (选择扇区、密钥类型)
   │ ─────────────────────────────►
   │  ② 发随机数 nt (32 bit)
   │ ◄─────────────────────────────
   │  ③ 用密钥加密 (nt, nr, ar…) 发回
   │ ─────────────────────────────►
   │  ④ 卡片验证，返回加密的 at
   │ ◄─────────────────────────────
```

关键在于**第 2 步卡片会无条件先吐一个 `nt`**，即使后面认证失败。这就给了攻击者「免费」的随机数观测。

### 3.2 mfkey32

如果你用一把**错误**的密钥发起认证，能记下一组：

```
uid, nt, nr_enc, ar_enc, at_enc
```

`mfkey32` 就是利用这些值之间的加密关系，把「正确的 48 bit 密钥」压缩成「只需穷举 32 bit」——计算量从 2^48 降到 2^32 以内，PC 上秒级可算。

本项目 `app/mfkey_local.py` 用 numba 加速，20 bit 的空间约 0.1 秒。

### 3.3 HardNested

有些卡（「全加密卡」）对错误密钥不吐 `nt`，`mfkey32` 就失效了。这时只能用 HardNested：收集大量 nonce 对，用统计学方法（card-only / reader-only 变体）求解。

HardNested 计算量很大（几分钟到几小时），所以只能在**设备端**做（固件有优化的采集和部分计算能力），或者用 PC 上的 `crack_engine.py` 长时间跑。

### 3.4 全卡破解策略

一张 Mifare Classic 有 16（或 40）个扇区，每个扇区有独立的 KEY A / KEY B。破解流程：

```
1. 先用默认密钥 FFFFFFFFFFFF 全卡扫一遍 → 明文卡秒杀
2. 查找本卡历史密钥库（之前成功过的直接复用）
3. 查全局密码库
4. 剩下的扇区逐个：
   4a. 能采到随机数 → mfkey32
   4b. 采不到 → HardNested
5. 命中一把密钥后立刻复扫其余扇区（同一张卡的密钥常重复）
```

`api.py` 的 `_crack_all_sectors()` 就是这个流程，带总时间预算和可取消。

## 五、几个容易踩的坑（写代码时可参考）

1. **4 字节 UID 必须反序**。设备返回 `A1 B2 C3 D4`，人看到的是 `D4 C3 B2 A1`。
2. **`0x17` 是封卡不是写块**。早期 `WRITE_FORMATS` 里误把 `0x17` 当写块候选，会导致误发不可逆指令。已移除。
3. **`0x24` 是卡号校验不是写块**。早期也误列入写块候选。
4. **`0x0A` AUTH 是空命令**。真正认证走 `0x06` / `0x09`，`0x0A` 永远回 `0A 00 00`。
5. **`0x41` BATCH_FIND 的 keyType 语义与 `0x06/0x09` 相反**：`1` 表示 KEY A。
6. **状态码位置不统一**。见 `STATUS_INDEX` 表。
7. **PC/SC 首次查卡片状态必然超时**。`SCARD_E_TIMEOUT`（0x8010000A）要当成功处理，状态在 `dwEventState` 里。
8. **信标是 4 段不是 5 段**。端口在 `parts[3]`。
9. **写块失败要回滚**。写完立刻读回校验，不一致就把原内容写回去（`_restore_block`）。
10. **非 BLE 通道要在方法入口就拦**。不要先发几个必然失败的 APDU 再报错，那样用户会白等超时。
